The agent loop (asked most often)

The tool use loop

1Send a user message in messages
→
2Look at stop_reason
→
3If tool_use, run the tool
→
4Return a tool_result in the user role (same tool_use_id)
→
5Repeat 2–4 until end_turn
The loop ends on stop_reason and nothing else. Options that stop because “the text says done”, “three tools were called” or “assistant text came back” are all wrong (text and a tool request can arrive together). max_tokens is a safety device, not a target.

4 workflow patterns + the agent

ChainingFixed steps in order. When a long list of constraints is not kept: draft → revise
RoutingClassify, then send to a dedicated handler. Enough when there are only a few paths
ParallelizationRun independent subtasks at once and combine the results
Evaluator-optimizerSeparate the writer from the judge; on a fail, regenerate with the feedback
AgentOnly when the steps cannot be listed in advance. Bound it with tool limits, a turn budget and a stop rule

Errors are handled by type

CodeMeaningCorrect handling
400 invalid_requestThe request is malformedFix it and send again. Retrying does nothing
401 / 403Authentication, permissionCheck the key and its permissions. Do not retry
404 not_foundModel name or resourceCheck the name
413 request_too_largeToo bigSplit or summarize
429 rate_limitRate limitExponential backoff with jitter · read retry-after
500 api_errorServer sideWait briefly and retry
529 overloadedOverloadedBack off · another route or a fallback
refusal (stop_reason)Safety refusalDo not work around it. Auto-retrying with new wording is a wrong answer
“Retry everything the same way” and “fall back on everything” are wrong. Retry only the transient ones (429/500/529), fix bad input (400), and do not work around a refusal.

Tools and MCP

Points not to drop

  • A tool definition = name, description (3–4 sentences: what it does, when to use it, what it returns) and input_schema (JSON Schema). If the wrong tool gets picked, fix the description first
  • tool_choice: auto (default) / any (must use one) / {type:"tool",name:…} (force a named tool) → the dependable way to get structured output
  • Guarantee the shape of structured output with tool use or the structured outputs feature. Always validate what you receive (errors of meaning remain)
  • Parallel tool calls: several tool_use blocks in one response. Return all the results together in one user message
  • The 3 MCP primitives: tools (the model calls them) / resources (the app reads them) / prompts (the user invokes them). Tool use and MCP are separate topics (who defines and runs the tool)
  • .mcp.json (project, shared, secrets expanded with ${ENV}) / ~/.claude.json (personal). An MCP tool with a thin description does not get picked

Security

Text from users or outside data mixed into instructions
○ PickDelimit untrusted input (XML tags), narrow permissions, inspect tool results too
× AvoidWriting “please ignore it” is enough / a filter alone is enough
Where the API key lives
○ PickServer side, environment variables, a secrets manager. No direct API calls from the client
× AvoidEmbedded in the front end / committed to the repository
Tool permissions
○ PickLeast privilege. Separate read from write. Confirm or get human approval for destructive actions
× AvoidOne broad permission because it is convenient
Output executed or displayed as is
○ PickValidate and sanitize first, above all HTML, SQL and commands
× AvoidAssuming model output is safe
