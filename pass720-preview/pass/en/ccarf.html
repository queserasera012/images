The agentic loop

The loop branches on stop_reason

1Send the request
→
2Look at stop_reason
→
3tool_use → run the tool
→
4Add the result to the conversation and resend
→
5End on end_turn
Options that use parsing the wording (“done”), an iteration count, or the fact that text came back as the stop condition are wrong. An iteration cap is a safety device, not a stop condition.

Multi-agent

Hub and spoke (subagents do not talk to each other)

CoordinatorDecomposes, delegates, synthesizes, judges quality
→
Task tool"Task" in allowedTools. Several Task calls in one response = parallel
→
SubagentAgentDefinition (description, prompt, tool limits). Cannot see the parent conversation
→
ReturnA structured result plus source metadata. Only a summary comes back

Points not to drop

  • Pass context explicitly: write the goal, findings so far, output format and constraints into the prompt. “The parent knows, so it carries over” is false
  • Pass sources as structure, apart from the body (claim ↔ source URL, date). This stops sources vanishing in synthesis
  • Narrow tools by role (4 or 5). 18 is too many and wrong picks go up
  • Partial failure: neither swallow it nor stop everything. Say what is missing and leave the decision to the coordinator
  • Shallow research → suspect the coordinator’s decomposition first (a subagent looks only where it is told)
  • Sessions: --resume if the context is valid; a new session from a structured summary if tool results are stale. fork_session to try an alternative

Prompting and structured output

The flow of structured extraction (scenario 6)

1Extract with tool plus JSON schema (forced by tool_choice)
→
2Schema validation (strict prevents syntax errors)
→
3Semantic validation (does the total add up, and so on)
→
4Retry with the error attached
→
5Only low-confidence fields go to a person

Points not to drop

  • Allow null for absent information (nullable). Make it required and it invents something. Classify with an enum plus "other" and a detail; use "unclear" when it cannot be decided
  • A schema prevents syntax errors, not semantic ones. Take both stated_total and calculated_total, and detect with conflict_detected
  • A retry works on errors of format and structure. Information that is not in the document never comes out
  • Few-shot: 2 to 4, with reasons, aimed at ambiguous boundaries. It also helps when the format varies
  • Precision: specific criteria (what is and is not reported; a code example per severity) beat “be conservative” or “only the important ones”. Pause a category with many false positives
  • Batches: 50% off, up to 24 hours, custom_id. No multi-turn tool use. Urgent work (pre-merge checks) is synchronous; overnight reports are batch. Resubmit only the failures

Context and reliability

○ PickA case facts block (customer ID, order, amount) at the top every time. Trim tool output to the fields needed
× AvoidLeaving it to progressive summarization (numbers get rounded)
The customer says “put me through to a person”
○ PickEscalate there and then
× AvoidTrying once more to resolve it / asking why
Criteria for escalation
○ PickAsked for a person · not in policy · no progress
× AvoidStrength of sentiment · the model’s self-reported confidence
Several customers match
○ PickAsk for further identifying information
× AvoidPicking the most plausible one
Handing over to a person
○ PickCustomer ID, root cause, amount, what was tried and recommended action, as structure
× AvoidPassing the conversation log as it is
Extraction is 97% accurate and you want less human checking
○ PickMeasure by type and by field. Stratified sampling; thresholds calibrated on a labeled set
× AvoidRemoving checks across the board on the overall figure
Sources disagree
○ PickShow both with source and date, and leave the decision to the level above
× AvoidQuietly adopting the newer one / averaging
