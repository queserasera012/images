エージェントのループ（最頻出）

ツール使用ループ

1messages に user を送る
→
2stop_reason を見る
→
3tool_use なら ツールを実行
→
4tool_result を user ロールで返す（同じ tool_use_id）
→
5end_turn になるまで 2〜4 を繰り返す
終了の判定は stop_reason だけ。「テキストに『完了』と書いてある」「ツールを 3 回呼んだ」「アシスタントのテキストが返った」で終わらせる選択肢は すべて不正解（テキストとツール要求は同時に返る）。max_tokens は目標ではなく安全装置。

ワークフロー 4 型 ＋ エージェント

チェーン手順を固定して順に。長い制約が守られないとき 下書き → 直す
ルーティング分類して専用の処理へ。経路が数通りに収まるなら これで足りる
並列化独立した小課題を同時に実行して集約
評価者・最適化生成役と評価役を分け、不合格ならフィードバックで作り直し
エージェント手順を事前に列挙できないときだけ。ツール制限・ターン予算・停止基準で縛る

stop_reason を全部言えるか

end_turn自然に終わった。ループ終了
tool_useツールを呼べと言っている。実行して tool_result を返す
max_tokens上限で切れた。続きを頼むか上限を見直す
stop_sequence指定した文字列が出た
pause_turn長いサーバーツール処理の途中。content をそのまま返して続行
refusal安全上の拒否。迂回しない・安全なフォールバック
model_context_window_exceededコンテキスト上限。要約・分割

エラーは種類で扱いが違う

コード意味正しい扱い
400 invalid_requestリクエストの形が悪い直して送る。再試行しても無駄
401 / 403認証・権限キーと権限を確認。再試行しない
404 not_foundモデル名やリソース名前を確認
413 request_too_large大きすぎる分割・要約
429 rate_limitレート制限指数バックオフ＋ジッター・retry-after を見る
500 api_errorサーバー側少し待って再試行
529 overloaded混雑バックオフ・別経路／フォールバック
refusal（stop_reason）安全拒否迂回しない。別の言い回しを自動で試す選択肢は不正解
「全部同じに再試行」「全部フォールバック」は不正解。一時的（429/500/529）だけ再試行、入力の誤り（400）は直す、拒否は迂回しない。

コストと速さ（計算問題が出る）

使い分け選ぶ場面ポイント
Message Batches API急がない・大量・コスト重視50% オフ・24 時間以内。非同期。結果はまとめて取る
プロンプトキャッシュ同じ長い前置きを何度も送るcache_control を安定した部分の末尾に。前方一致。固定を先・変動を後。短すぎるとエラー無しで効かない
ストリーミング体感の速さ（TTFT）を縮めたい全体の時間は変わらない。長い出力の UX 向け
モデルの階層Haiku（速い・安い・定型）／Sonnet（既定）／Opus（難しい判断）上位モデルを常に選ぶのは誤り。評価で決める
拡張思考多段階の推論が要るときだけ分類・抽出では遅延と費用が増えるだけ。budget_tokens
キャッシュの診断：cache_read_input_tokens が増えていれば効いている。cache_creation_input_tokens が毎回出るなら 先頭に変わる値（日時・ユーザー名）が混ざっている。

ツールと MCP

落とさないポイント

  • ツール定義＝ name・description（3〜4 文：何をする・いつ使う・何を返す）・input_schema（JSON Schema）。誤ったツールが選ばれるなら 説明文を直すのが先
  • tool_choice：auto（既定）／any（必ずどれか）／{type:"tool",name:…}（指定ツールを強制）→ 構造化出力の確実な取り方
  • 構造化出力はツール使用か構造化出力機能で形を保証。受け取ったら必ず検証（意味の誤りは残る）
  • 並列ツール呼び出し：1 応答に複数の tool_use。結果はまとめて 1 つの user メッセージで返す
  • MCP の 3 プリミティブ：ツール（モデルが呼ぶ）／リソース（アプリが読む）／プロンプト（利用者が起動）。ツール利用と MCP は別の話（誰が定義・実行するか）
  • .mcp.json（プロジェクト・共有・${ENV} で秘密を展開）／~/.claude.json（個人）。説明が貧弱な MCP ツールは選ばれない

Claude Code（3%・最低限）

CLAUDE.md規約・コマンド・触らない場所。毎回読まれる
権限モードdefault／acceptEdits／plan／auto／dontAsk（無人）／bypassPermissions（隔離のみ）
設定の優先管理設定 ＞ CLI ＞ ローカル ＞ プロジェクト ＞ ユーザー
フックPreToolUse で止める。終了コード 2 がブロック、1 は止まらない
Skill／スラッシュコマンド手順を包む。助言的。保証はフック
サブエージェント別コンテキスト。要約だけ返る

セキュリティ

ユーザーや外部データの文を指示に混ぜる
○ 選ぶ信頼できない入力は区切る（XML タグ）・権限を絞る・ツール結果も検査
× 選ばない「無視してください」と書けば防げる／フィルタだけで十分
API キーの置き場
○ 選ぶサーバー側・環境変数・秘密管理。クライアントから API を直接呼ばない
× 選ばないフロントエンドに埋め込む／リポジトリにコミット
ツールの権限
○ 選ぶ最小権限。読み取りと書き込みを分ける。破壊的操作は確認か人の承認
× 選ばない便利だから広い権限を 1 つ
出力をそのまま実行・表示する
○ 選ぶ検証・サニタイズしてから。HTML・SQL・コマンドは特に
× 選ばないモデルの出力は安全という前提

直前チェック（当日）

  • stop_reason を 7 つ言える（end_turn / tool_use / max_tokens / stop_sequence / pause_turn / refusal / model_context_window_exceeded）
  • ストリーミングのイベント順を言える
  • tool_result は user ロール・同じ tool_use_id・並列はまとめて 1 メッセージ
  • 429 / 529 はバックオフ、400 は直す、refusal は迂回しない
  • Batches 50% オフ 24 時間・キャッシュは前方一致で固定を先
  • tool_choice の 3 つと構造化出力の「受け取ったら検証」
  • Haiku / Sonnet / Opus の使い分けと「常に上位は誤り」
  • MCP の 3 プリミティブと誰が制御するか
  • 権限モード 6 つ・フックの終了コード 2・設定の優先順
  • API キーはサーバー側、信頼できない入力は区切る
  • 評価は 成功基準 → データセット → 自動採点 の順
  • D2 と D5 を先に解き、D3・D4 は最後
