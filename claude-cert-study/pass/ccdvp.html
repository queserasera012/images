本番の統合・信頼性・グラウンディング（20%・最重点）

エラーは種類で分ける（「全部再試行」「全部フォールバック」は不正解）

起きたこと正しい扱い
429 レート制限指数バックオフ＋ジッター・retry-after
529 overloadedバックオフ・別経路／フォールバック
安全性の拒否（refusal）迂回しない。安全なフォールバック・人へ
max_tokens で切れた続きを生成・上限を見直す
invalid_request（400）直して送る（再試行しても同じ）
pause_turncontent をそのまま返して続行

どの制約に当たっているか

429 の率・残り枠＝ レート制限
1 分あたりのトークン＝ スループット
完了時間と単価＝ バッチの経済性

RAG は段階ごとに診断（前から順に）

取り込みチャンクが切れていないか
→
検索再現率：正解の文書が候補に入っているか
→
リランキング適合率：上位に来ているか
→
生成根拠を使っているか・引用

落とさないポイント

  • 固有名詞・型番・ID が拾えない → ハイブリッド検索＋メタデータ（ベクトルだけでは弱い）
  • 正解の文書が候補に無いのに プロンプトを直すのは不正解（検索の問題を生成で直さない）
  • 根拠を示させたい → 引用（citations）。引用できない主張は出さない設計に
  • キャッシュ：前方一致。ブレークポイントは安定した部分の末尾。cache_read_input_tokens が増えれば効いている。cache_creation_input_tokens が毎回 ＝ 先頭に変わる値。変更は境界より後ろに
  • ツール定義は最後のツールに cache_control で全体がキャッシュ。1 つ変えると全体が無効。最小長未満はエラー無しで効かない
  • 構造化出力で形を保証しても 意味の検証は自分で

1σ記録のみ
→
2σ読み取り専用で診断
→
3σPR か事前承認済みの手順書に限って行動

落とさないポイント

  • 検知にモデルを使わない（統計の規則で検知 → 診断にモデル）
  • ゆっくりした悪化は 個々のトレースでは見えない → 連続性の規則（同じ側に連続）で拾う
  • 監査ログに要るもの：誰（エージェントと代理するユーザー）・どのツール・どの引数・いつ・結果
  • 支出：既定のモデルと effort が上限の変更より効く。上限引き上げの依頼は原因を調べるきっかけ

評価エンジニアリング（12%）

ジャッジ（LLM 審査）のバイアス 4 つ

冗長性長い答えを高く付ける → 長さを評価しない基準
位置先に出た方を選ぶ → 順序を入れ替えて 2 回
自己選好自分の系統を好む → 別系統のモデル
ドリフトジャッジの版が変わると基準が動く → 再キャリブレーション

評価器も AI レビューも：人と比べてから権限を与える

シャドー権限なしで並走
→
キャリブレーション人との一致率・偽陽性率
→
限定ゲート重大な指摘だけブロック
→
拡大

落とさないポイント

  • 設定の変更も eval で回帰：CLAUDE.md・Skill・ツール説明・モデル・effort を変えたら走らせる
  • 「十分な数字」の罠：正答率 93% でも 失敗が 1 種類に固まっていないか。一致率 71% は偶然の一致を引いて見る
  • 採点は コード（決定的）→ LLM ジャッジ → 人 の順に安い方から
  • 本番の失敗は eval セットに還流させる

  • キャッシュ：前方一致・creation 毎回＝先頭が可変・最後のツールに cache_control
  • 記録 3 種（Compliance API／監査ログ／OpenTelemetry）
  • 管理帯 1σ／2σ／3σ。検知にモデルを使わない
  • インシデント：影響 → ロールバック → 告知 → 調査 → 回帰
  • ジャッジのバイアス 4 つと対策
  • シャドー → キャリブレーション → 限定ゲート

  • 致死的な三要素・PreToolUse 終了コード 2・サンドボックス
